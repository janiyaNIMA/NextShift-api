1. System Overview & Problem Domain

UniShift: Campus Part-time Job Marketplace Backend

Architecture

UniShift (NextShift) is a production-ready REST API platform built to connect university students with on-campus and local business vacancies.


Key Domain Roles:

  • Students: Discover vacancies, book shifts, track booking status.
  • Employers: Post shifts, manage shift capacity, review student bookings.
  • Admins: Verify employers and approve job posts before public release.

Layered Architectural Flow

[ HTTP Client / Web Client ] │ JSON Request + Bearer JWT ▼ [ REST Controllers ] (Presentation Layer) │ Domain method calls ▼ [ Services ] (Transactional Business Logic) │ │ ▼ ▼ [ Strategy Engine ] [ Repositories ] (Data Access) │ │ └─────────┬─────────┘ ▼ [ MySQL / H2 Database ]
Notes: UniShift backend එක 3-Tier Layered Architecture එකක් අනුගමනය කරනවා. Controllers HTTP requests හසුරුවනවා, Services තුළ business logic සහ transaction boundaries තියෙනවා, Repositories හරහා data persistence සිද්ධ වෙනවා.

2. OOP Pillars in UniShift Summary

How core OOP concepts map directly to our code

Pillars

1. Encapsulation (කැප්සියුලීකරණය)

Fields declared private. State changes guarded by domain methods (job.publish(), user.approve()). Request/Response DTOs defined as immutable Java 21 record types.

2. Abstraction (වියුක්තකරණය)

Abstract mapped superclass BaseEntity hides persistence ID and timestamp mechanics. JobRecommendationStrategy isolates query complexity from services.

3. Polymorphism (බහුරූපතාවය)

Strategy Pattern allows dynamic runtime swapping of recommendation algorithms. UserPrincipal acts polymorphically as Spring Security's UserDetails.

4. Inheritance (උරුමය)

BaseEntity is extended by User, Job, and Booking. Custom ApiException hierarchy unifies REST error handling and HTTP status mappings.

Notes: වස්තු-පාදක ක්‍රමලේඛනයේ ප්‍රධාන කුළුණු 4ම UniShift තුළ භාවිත කර ඇත. Encapsulation මඟින් දත්ත ආරක්ෂාව, Abstraction මඟින් සංකීර්ණතා සඟවා තැබීම, Polymorphism මඟින් පද්ධතියේ නම්‍යශීලී බව, සහ Inheritance මඟින් කේත නැවත භාවිතය (reusability) තහවුරු කර ඇත.

5. Subclasses & Hierarchies (අනුපන්ති)

Specialized child classes extending parent functionality

Subclasses

1. Entity Subclasses

User, Job, and Booking extend BaseEntity.

@Entity
public class Job extends BaseEntity {
    private String title;
    private JobStatus status;
    // Inherits id, createdAt, updatedAt
}

2. Exception Subclasses

Specialized REST HTTP exceptions extend ApiException:

public class ConflictException 
    extends ApiException {

    public ConflictException(String msg) {
        super(msg, HttpStatus.CONFLICT);
    }
}

3. Security Filter Subclass

JwtAuthenticationFilter extends OncePerRequestFilter: Specializes Spring Security's base filter to intercept HTTP requests and validate JWT tokens.

Notes: Subclass එකක් මඟින් parent class එකේ fields සහ methods inherit කරගන්නවා. අපේ project එකේ BaseEntity එකෙන් entities 3ක් සහ ApiException එකෙන් ConflictException, ResourceNotFoundException ආදී exceptions inherit වෙනවා.

6. Interfaces (අතුරුමුහුණත්)

Decoupling specifications from concrete implementations

Interfaces

The Strategy Contract:

package com.unishift...recommendation;

public interface JobRecommendationStrategy {
    
    Page<Job> getRecommendedJobs(
        Long studentId,
        String category,
        String location,
        Pageable pageable
    );
}
  • Defines what needs to be computed without binding to how.
  • Enables Dependency Inversion Principle (DIP).

Persistence Interfaces:

public interface JobRepository 
    extends JpaRepository<Job, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    Optional<Job> findByIdWithLock(Long id);
}

Security Interfaces:

UserDetails and UserDetailsService provide standardized framework contracts implemented by UserPrincipal and CustomUserDetailsService.

Notes: Interface එකක් කියන්නේ contract එකක්. JobRecommendationStrategy මඟින් රැකියා තෝරාදීමේ algorithm එක service layer එකෙන් සම්පූර්ණයෙන්ම වෙන් (decouple) කරලා තියෙනවා.

7. Polymorphism: Strategy Pattern

Subtype Polymorphism enabling dynamic algorithm injection

Polymorphism

1. Consumer depends on Interface:

@Service
public class JobService {
    // Injected polymorphically
    private final JobRecommendationStrategy strategy;

    public Page<JobResponse> getPublishedJobs(...) {
        // Polymorphic dispatch at runtime
        Page<Job> jobs = strategy.getRecommendedJobs(...);
        return jobs.map(JobResponse::fromEntity);
    }
}

2. Concrete Implementation:

@Component
@Primary
public class AllPublishedJobsStrategy 
    implements JobRecommendationStrategy {

    @Override
    public Page<Job> getRecommendedJobs(...) {
        return jobRepository.findEligibleJobs(...);
    }
}
Open/Closed Principle (OCP) In Action: If tomorrow we build an AI-based or GPS-distance ranking engine, we write a new class implementing JobRecommendationStrategy. JobService and JobController require zero modifications!
Notes: Polymorphism හෙවත් බහුරූපතාවය මෙහි ප්‍රධාන ලෙස Strategy Pattern හරහා යොදාගෙන තිබෙනවා. JobService එක direct class එකක් වෙනුවට JobRecommendationStrategy interface එක call කරන නිසා, runtime එකේදී කැමති algorithm එකක් switch කරන්න පුළුවන්.

8. Method Overriding & Overloading

Runtime vs. Compile-time Polymorphism in UniShift

Polymorphism

Method Overriding (Dynamic Polymorphism)

Providing specialized subclass behavior for inherited methods:

// In BaseEntity.java: Overriding Object.equals
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) 
        return false;
    BaseEntity that = (BaseEntity) o;
    return id != null && Objects.equals(id, that.id);
}

Guarantees entity equality is determined strictly by persistent primary key identity.

Method Overloading (Static Polymorphism)

Same method name with different parameter signatures:

// In JwtService.java: Overloaded token generator
public String generateToken(UserDetails userDetails) {
    return generateToken(userDetails, Collections.emptyMap());
}

public String generateToken(
    UserDetails userDetails, 
    Map<String, Object> extraClaims
) {
    // Generates token with extra role/user claims
}
Notes: Overriding යනු මව් පන්තියේ ඇති method එකක් child class එක තුළ අලුතින් ලිවීමයි (@Override). Overloading යනු එකම නම ඇති නමුත් parameters වෙනස් methods එකම class එක තුළ ලිවීමයි.

9. Encapsulation: Data Hiding & Rich Models

Guarding business invariants within entities

Encapsulation

Strict Data Hiding:

  • All fields in User, Job, and Booking are private.
  • Direct external modification is prohibited.

Rich Domain Methods in Job.java:

// Atomic state transition
public void publish() {
    this.status = JobStatus.PUBLISHED;
    this.publishedAt = Instant.now();
}

public void reject() {
    this.status = JobStatus.REJECTED;
}

Encapsulated Business Rule:

public boolean isEligibleForBooking(Instant now) {
    return this.status == JobStatus.PUBLISHED
            && this.employer != null
            && this.employer.isActive()
            && this.employer.isApproved()
            && this.startsAt.isAfter(now);
}
  • Prevents Anemic Domain Models.
  • Keeps domain rules bundled directly with the data they evaluate.
Notes: Encapsulation හිදී fields `private` කිරීම පමණක් නොව, state changes සඳහා ආරක්ෂිත methods (Rich Domain Model) සෑදීම සිදු කර ඇත. උදාහරණයක් ලෙස job.publish() මඟින් status සහ publishedAt එකවර update වේ.

10. Encapsulation: Immutability with Records

Tamper-proof DTOs using Java 21 Records

Encapsulation 
public record CreateJobRequest(
    @NotBlank String title,
    @NotBlank String description,
    @NotBlank String category,
    @NotBlank String location,
    @NotNull @DecimalMin("0.01") BigDecimal payAmount,
    @NotBlank String payUnit,
    @NotNull Instant startsAt,
    @NotNull Instant endsAt,
    @NotNull @Min(1) Integer capacity
) {}

Why Java 21 Records?

  • Built-in Encapsulation: All fields are automatically private and final.
  • No Setter Pollution: Records cannot be modified after construction $\rightarrow$ Immutability.
  • Thread-Safe: Safe to share across asynchronous and multi-threaded contexts without concurrency bugs.
  • Boundary Isolation: Client API requests cannot corrupt or mutate internal entity representations.
Notes: API එකෙන් එන සහ පිටවන දත්ත (DTOs) සඳහා Java 21 Records භාවිතා කර ඇත. Records වල සියලුම fields immutable (final) වන බැවින්, දත්ත අතරමගදී වෙනස් විය නොහැකි අතර පද්ධතියේ Thread-safety ආරක්ෂා වේ.

11. Abstraction (වියුක්තකරණය)

Hiding underlying mechanics behind clean interfaces

Abstraction

1. Abstract Class: BaseEntity

Abstracts ID generation, creation timestamps, and lifecycle callbacks (@PrePersist, @PreUpdate) so entity subclasses never handle audit plumbing.

2. Recommendation Abstraction

JobRecommendationStrategy abstracts complex database queries, pagination, and sorting from JobService and JobController.

3. Repository Abstraction

Spring Data JPA abstracts JDBC drivers, connection pools, and raw SQL behind simple, expressive Java method declarations.

Architectural Abstraction: Three-Tier Decoupling

Controllers abstract HTTP protocols  $\rightarrow$  Services abstract business rules  $\rightarrow$  Repositories abstract persistence  $\rightarrow$  Database abstracts physical storage.

Notes: Abstraction මඟින් අභ්‍යන්තරයේ සිදුවන සංකීර්ණ තාක්ෂණික කාර්යයන් සඟවයි. BaseEntity abstract class එක මඟින් ID සහ Timestamps හසුරුවන ආකාරය සඟවා ඇති අතර, Repository මඟින් SQL සහ database queries සඟවා ඇත.

12. Inheritance & Architectural Decisions

When to use Inheritance vs. "Favor Composition over Inheritance"

Inheritance

Where We Used Inheritance:

Technical Infrastructure Reuse:

  • BaseEntity $\rightarrow$ User, Job, Booking.
  • ApiException $\rightarrow$ ConflictException, ResourceNotFoundException, etc.
  • OncePerRequestFilter $\rightarrow$ JwtAuthenticationFilter.

Outcome: DRY (Don't Repeat Yourself) compliance and uniform timestamp auditing.

Where We Avoided Inheritance:

Entity Roles: "Favor Composition":

Why not Student extends User in JPA?

  • JPA Pitfall: Table inheritance creates sparse tables with NULL columns or expensive SQL JOINs.
  • Our Solution: Composition via UserRole enum and boolean flags. Allows clean querying and zero database join overhead.
Notes: Inheritance තාක්ෂණික පොදු දේවල් සඳහා (BaseEntity, Exceptions) යොදාගන්නා ලදී. නමුත් UserRole සඳහා Student extends User ලෙස JPA table inheritance නොසාදා, Composition (Favor composition over inheritance) මූලධර්මය පිළිපදින ලදී.

13. SOLID Principles in UniShift

Industry best practices applied throughout the codebase

SOLID
Principle Implementation in UniShift
S - Single Responsibility Strict separation: Controllers (HTTP), Services (Domain rules), Repositories (Data access).
O - Open/Closed JobRecommendationStrategy can be extended with new algorithms without modifying JobService.
L - Liskov Substitution AllPublishedJobsStrategy seamlessly substitutes JobRecommendationStrategy. UserPrincipal substitutes UserDetails.
I - Interface Segregation Small, purposeful interfaces (e.g. JobRecommendationStrategy defines only one focused method).
D - Dependency Inversion JobService depends on the abstraction JobRecommendationStrategy, not the concrete implementation.
Notes: SOLID මූලධර්ම පහම අපගේ කේතය තුළ නිරූපණය වේ. විශේෂයෙන් Dependency Inversion සහ Open/Closed මූලධර්ම recommendation engine එක තුළ Strategy Pattern මඟින් පැහැදිලිව ක්‍රියාත්මක කර ඇත.

14. Viva / Evaluation Questions Cheatsheet

Common questions panelists ask and how to answer them

Viva Q&A
Q1: Where did you use the Strategy Pattern?
Answer: In JobRecommendationStrategy interface and AllPublishedJobsStrategy implementation injected into JobService. Demonstrates Subtype Polymorphism and OCP.
Q2: Why use `BaseEntity`?
Answer: Encapsulates common persistence state (id, createdAt, updatedAt) and lifecycle hooks (@PrePersist). Promotes Abstraction and Inheritance (DRY principle).
Q3: How do you prevent anemic domain models?
Answer: Via Encapsulation. Entities expose domain methods with business invariants (e.g., job.publish(), job.isEligibleForBooking()) rather than blind setters.
Q4: Why not create `Student` and `Employer` as subclasses of `User` in JPA?
Answer: To prevent relational database overhead (joins or sparse null columns), following the OOP principle: "Favor composition over inheritance for entity roles".
Notes: Viva එකේදී අහන ප්‍රධාන ප්‍රශ්න 4ට කෙටි සහ නිවැරදි තාක්ෂණික පිළිතුරු මෙහි දක්වා ඇත.
